# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  - 素のLLMは「LoRAとは？」と聞いたときに、一般的な説明をそのまま返すだけで、講義の定義や回数の情報を明示しないことが多い。
  - エージェントでは `search_glossary` を使って用語集を確認し、講義の定義を参照して回答するので、より講座に沿った説明になる。
  - また、最終的に「第2回」といった関連回を示して、学習の文脈を付けている。
- `--trace` で見えたツール呼び出し（ツール名と引数）：
  - `search_glossary({'query': 'LoRA'})`
  - つまり、モデルが「LoRA」という用語を検索し、用語集の定義と関連情報を取りに行っていた。
- 1つの質問での LLM 呼び出し回数（`requests`）：
  - `requests=2`
  - `--trace` の実行結果では、1回の質問に対してモデルの利用が2回発生しており、そのうち1回がツール実行後の最終回答を生成する流れだった。
- 追加したツールと、docstring に書いた説明：
  - `search_glossary(query: str)`: 「講座の用語集から用語を検索し、定義とどの回で扱うかを返す」
  - `get_lecture_summary(lecture: int)`: 「指定した回の講義の要点を返す」
  - `make_quiz(lecture: int)`: 「指定した回の用語から1つを選び、確認問題と答えを返す」
  - これらの docstring をそのままツール説明としてモデルに渡しており、どのときにどのツールを使うかが変わる。

## 宿題

- 取り組んだレベル：実装
- やったこと：
  - 用語検索、講義要約、確認問題生成の3つのツールを追加し、講義ごとに自然に使い分けられるようにした。
  - 例外パターンを考慮し、存在しない回を指定したときにも落ちずにエラーを返すようにした。
  - ラッパー側で、ユーザーの質問そのものではなく、ツールが返した問題と答えを保存するように整えた。これにより、ログの品質と再現性を担保した。
  - さらに、保存先を lecture ごとに分けて整理し、学習ログの形式を定型化した。
- 結果：
  - 16件のテストが通過した。
  - 実際にエージェントで確認問題を生成し、その結果が data/learning_log 配下に lecture ごとの JSONL として保存されることを確認した。
  - これで、学習の記録として「どの回の何を学んだか」を後から追いやすくなった。
- 気づき・疑問：
  - 「ツールを作る」だけでなく、ラッパーで結果の整形や保存をまとめておくと、AIの出力のばらつきを吸収しやすくなる。
  - そのため、今回の工夫は「機能追加」だけでなく「品質担保」の側面が大きかったと感じた。
  - ただし、今後はログの保存対象をもっと厳密に決めると、学習ログの使い勝手がさらに上がりそうだ。
